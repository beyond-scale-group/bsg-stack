# ADR-003: `DESIGN.md` schema — adopt Google Stitch spec

- **Status:** Accepted
- **Date:** 2026-05-05
- **Resolves:** #237 (block-A4), #555
- **Depends on:** ADR-001 (`.bsg/` directory convention)

## Context

#237 introduces `.bsg/DESIGN.md` as the canonical visual-identity
artifact for a repo. It is consumed by:

- **md-to-office** — generates branded Office templates (`.docx`,
  `.pptx`) using fonts, colors, and spacing from `DESIGN.md`. Today
  the same data lives in `brand/tokens.json`, generated by
  `scan-brand.py`.
- **frontend-design** — generates UI components consistent with the
  brand. Today reads CSS / Tailwind directly.
- **storytelling** — cross-references the visual identity (DESIGN.md)
  with the voice (NARRATIVE.md) for holistic brand audits.

#555 block-A4 calls out the unresolved question:

> Adopt Google Stitch DESIGN.md spec verbatim, or define a BSG schema?
> Whether `brand/tokens.json` becomes derived or stays primary.

Without a schema commitment, every consumer agent has to re-invent
its own parser, and the migration from `brand/tokens.json` is
ambiguous (is it primary, derived, or just deprecated?).

## Decision

1. **Adopt the Google Stitch DESIGN.md specification verbatim** as
   the schema for `.bsg/DESIGN.md`. We do not invent a BSG variant.
2. **`brand/tokens.json` becomes derived** — generated from
   `DESIGN.md`, never hand-edited. md-to-office reads either path
   transparently during the migration window, then drops the JSON
   read once all consumer repos have re-generated.

### Why Google Stitch

- It already exists, is open-spec'd, and is published with the
  explicit goal of being machine-consumable by AI agents (per the
  Google Labs announcement).
- Covers everything the consumer agents need: **colors** (semantic
  palette), **typography** (per-usage stacks), **spacing & layout**,
  **components** (button / card / form patterns), **accessibility**
  (WCAG contrast, focus indicators, motion preferences).
- Reading and writing it is a single Markdown parse — no new YAML
  schema, no JSON-LD, no third-party validator dependency.
- Avoids "yet another token format" — the world has Style Dictionary,
  Figma tokens, design tokens W3C draft. Picking one of those
  re-opens the format war; picking a sibling spec sidesteps it.

### Schema mapping (consumer expectations)

The Stitch sections map to consumer agents as follows:

| Stitch section | Consumed by | Field used |
|---|---|---|
| `## Colors` | md-to-office, frontend-design | `primary`, `secondary`, `accent`, `background`, `text` (semantic names, hex values) |
| `## Typography` | md-to-office, frontend-design | `heading`, `body`, `caption`, `code` font stacks; sizes/line-heights |
| `## Spacing` | md-to-office (margins), frontend-design (grid) | scale (xs/sm/md/lg/xl) → numeric values |
| `## Components` | frontend-design | optional; advisory pattern hints |
| `## Accessibility` | all consumers | WCAG ratio target, motion-reduce default |

Consumers MUST handle missing sections gracefully — a repo without a
`Components` section should not crash the renderer.

### Migration: `brand/tokens.json` is derived

Today: `scan-brand.py` extracts CSS / Tailwind / package.json
signals into `brand/tokens.json`, which md-to-office reads.

After this ADR:

1. **`scan-brand.py --emit design-md`** generates `.bsg/DESIGN.md`
   from the same scan sources. This becomes the primary `--init`
   output for md-to-office.
2. **`tokens-from-design.py`** (new helper) projects the Stitch
   subset md-to-office needs into `.bsg/brand/tokens.json`. Run as
   a build step; the JSON is regenerated, not hand-edited.
3. **md-to-office** reads `tokens.json` for now (existing path).
   Once `tokens-from-design.py` is wired, the templates pipeline is
   unchanged — same JSON shape, different upstream source.
4. **Eventual goal:** md-to-office reads `DESIGN.md` directly and
   `brand/tokens.json` is dropped. Not in scope for this ADR; that's
   a later child of #237.

This means the v1 of `--init` for md-to-office still emits
`brand/tokens.json` — but it now ALSO emits `.bsg/DESIGN.md` as the
human-editable source, with `tokens.json` as the derived artifact.

### What this ADR does NOT decide

- The exact Stitch field-name → tokens.json key mapping (lives in
  `tokens-from-design.py` once written).
- Whether DESIGN.md should ALSO be linted / validated by the unit
  test suite. Probably yes; out of scope here.
- Whether storytelling's voice + design cross-audit is a new agent
  feature or a `/bsg-stack` doctor row. Out of scope.

## Consequences

**Positive**

- One schema, one parser, one source of truth across every consumer.
- Open spec → repos with existing Stitch DESIGN.md (Google internal,
  partner repos) work with BSG agents zero-config.
- Hand-editable: a designer can update colors in Markdown without
  touching JSON.
- `tokens.json` stays for md-to-office's existing pipeline — no
  rendering regression.

**Negative / Risks**

- We're committing to a third-party spec. If the Stitch spec evolves
  in a backwards-incompatible way, we either pin or follow.
  Mitigation: copy the spec snapshot to `.bsg/adr/003-design-md-schema-stitch-snapshot.md`
  if/when needed (not in scope for this ADR).
- `tokens.json` derived-not-primary is a subtle invariant — someone
  hand-editing it will get clobbered on next `--init`. We add a
  header comment to the generated file: "DERIVED FROM
  `.bsg/DESIGN.md` — do not edit by hand."

**Neutral**

- Existing repos with `brand/tokens.json` and no `DESIGN.md` keep
  rendering. The migration is opt-in per repo: run `--init` to
  generate `DESIGN.md`, then commit. No flag-day cutover.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Define a BSG-specific schema | Re-invents what Stitch already specifies. We get to skip a design committee. |
| Style Dictionary / W3C design tokens | JSON-first. Less editable by designers. Heavier tooling stack. |
| Keep `brand/tokens.json` primary, no DESIGN.md | Loses the Markdown-editability win. Doesn't help frontend-design or storytelling. |
| Ship DESIGN.md + drop `tokens.json` immediately | Breaks md-to-office's existing pipeline. Forces a flag-day migration of every consumer repo. |
